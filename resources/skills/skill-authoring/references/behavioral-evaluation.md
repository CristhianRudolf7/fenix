# Evaluating a skill change / Evaluar cambios de skills

Use when a skill change is meant to improve decisions, execution quality or efficiency.

Keep three claims separate:

1. **Packaging:** valid metadata, real tools, loadable references, intact permissions and preserved customizations.
2. **Discovery:** representative user requests retrieve the intended candidate; unrelated requests do not acquire a new mandatory workflow.
3. **Behavior:** the consuming model completes the task more reliably or economically with the candidate instructions.

A passing parser, keyword check or retrieval test establishes only its own layer. Do not label any of those a model-quality benchmark.

Before editing, retain the relevant baseline text/version and define scenarios and scoring. Include the observed failure, a distinct transfer case and a case that should not activate the procedure. Useful pressure cases include a tempting but incorrect reviewer suggestion, successful stale tests after a later code change, a passing test that never exercised the defect, and a request for a small edit that should proceed without a new approval ceremony.

For behavioral trials, use fresh isolated task state and the same model, settings, tools, permissions and resources for baseline and candidate. Keep the realistic surrounding prompt. Score observable artifacts, executed actions and correctness rather than recited skill rules. Repeat variable cases, retain failures/timeouts and record time, tokens and missing usage. A single improved example is exploratory evidence; a general superiority claim needs held-out tasks and an adequate sample.

Match the revision to the evidence: improve triggers for missed retrieval, provide a concrete output contract for omissions, and use conditional guidance for a decision that applies only in one situation. Prefer a narrow addition to another blanket prohibition. Do not require new agents, providers or paid calls when unavailable or outside the task's authorization. Record behavioral evaluation as not run when only deterministic checks are available.

## Español

Separa formato e instalación, descubrimiento y comportamiento del modelo. Conserva la versión anterior y fija escenarios antes de editar, incluyendo el fallo observado, transferencia y casos donde no debe activarse. Compara tareas aisladas con igual modelo, contexto, herramientas y permisos; puntúa resultados y acciones, no repetición de reglas. Retén fallos y mide recursos sin inventar datos. Una prueba léxica no demuestra más aciertos del modelo. Si no hubo evaluación conductual, decláralo y evita afirmaciones generales de superioridad.
