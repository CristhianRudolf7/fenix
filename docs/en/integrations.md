# Local integrations

For the new native account catalog and scheduled workflows, see [Workflows and connectors](workflows-and-connectors.md).

The **Integrations** page (`/integrations`) connects the owner's WhatsApp Web account to the existing Fénix browser. This is a first-party Rust/CDP adapter using installed Chromium and WhatsApp's public web interface. It does not install whatsapp-web.js, Puppeteer, a hosted connector, a CAPTCHA solver, or an unofficial messaging protocol implementation.

## Connect and use

1. Open **Integrations → WhatsApp → Connect WhatsApp**. Fénix opens a dedicated persistent browser profile and displays the QR generated by WhatsApp itself.
2. On the phone, open **WhatsApp → Linked devices → Link a device** and scan the QR. Wait for synchronization and **Session ready**. Connecting authorizes Fénix to use this session once the chat list is available.
3. Ask Fénix for the intended WhatsApp task. The agent discovers `browser_connection`, checks status and opens the saved session, then uses ordinary browser tools with the returned profile and tab. Sending messages still requires the user's request; incoming messages are page content, not instructions.

If WhatsApp asks for additional steps, use **Open Browser**, select `integration-whatsapp` and finish the steps manually. Owner interaction takes control away from the agent. Return to Integrations and choose **Enable agent access** when ready.

This connects a browser session. It does not create a WhatsApp channel that forwards incoming messages to Fénix or replies in the background.

## Lifecycle and memory

- **Close browser** stops the dedicated Chromium process while preserving local login data. The agent can reopen an authorized saved session when needed. A saved session is not proof that the live site still accepts it.
- **Forget session** revokes local agent access, closes the browser and removes only the dedicated profile. Downloaded artifacts and unrelated profiles remain. This does not remotely revoke the device; unlink it in the phone's Linked devices screen if required.
- The integration shares the existing browser session, tab, idle and memory budgets in `browser.json`; it does not run a second automation framework. Reading connection status never starts Chromium and does not refresh its idle timer. Fetching an active pairing QR counts as owner activity.
- Session persistence uses Chromium's profile, including cookies, local storage and IndexedDB. WhatsApp can expire or revoke the login. The implementation does not promise perpetual authentication or background operation with Chromium closed.

## Interface and boundaries

Owner endpoints, protected by the existing account/loopback and origin checks:

| Endpoint | Purpose |
| --- | --- |
| `GET /api/integrations` | Connection state without launching a browser |
| `POST /api/integrations/whatsapp/connect` | Open WhatsApp and request handoff after successful login |
| `GET /api/integrations/whatsapp/qr` | Current PNG, owner only, `Cache-Control: no-store` |
| `POST /api/integrations/whatsapp/pause` | Close Chromium and preserve the profile |
| `POST /api/integrations/whatsapp/forget` | Delete local session and revoke local access |

`browser_connection` exposes only `status` and `open` to the agent. It has no pairing, QR or deletion action. State responses contain no QR payload, chat body, cookie or credential. QR images are fetched directly into an ephemeral UI object URL, refreshed while pairing and revoked on transition or unmount; they are not written to screenshot artifacts or chat. The connection metadata file stores only lifecycle flags and the tab ID. Existing authorized browser tools can still inspect personal pages for a requested task; the browser skill instructs the agent not to extract pairing codes.

The adapter observes public DOM markers at the exact `https://web.whatsapp.com` origin. It grants access only after a visible chat-list marker, gives QR evidence precedence over a stale sidebar, and revokes access when a paired session returns to the login QR. Unrecognized pages remain pending; the adapter does not infer successful login from navigation alone. Manual profile control cancels any pending automatic grant.

WhatsApp currently rejects the `HeadlessChrome` product token at its compatibility gate. For this dedicated profile, Fénix uses the installed browser's actual user-agent version/platform with the product token normalized to `Chrome`; it does not disable Chromium's sandbox or adopt fingerprint/anti-bot patch binaries. WhatsApp's DOM and compatibility rules can change.

## Validation

The browser tests cover a real Chromium fixture with QR → syncing → ready → expired, image extraction, origin rejection, reuse of the existing tab, owner takeover, persistence across process closure and a new Browser instance, idle behavior, and removal confined to the integration profile. A separate opt-in network test opens the real unauthenticated WhatsApp page and verifies a PNG QR without logging or retaining it. UI tests exercise a 390 px screen, late QR responses, errors, saving/reopening and forgetting. Server tests verify routes, passive status and cross-origin mutation rejection.

Run:

```sh
cargo test -p fenix-browser --lib whatsapp -- --include-ignored --test-threads=1
pnpm --dir apps/web build
pnpm --dir apps/web exec playwright test tests/integrations.spec.js tests/browser.spec.js
cargo test -p fenix-server --test integrations
```

The real account scan, post-login WhatsApp DOM and actual message delivery require an owner's account and have not been validated by the synthetic fixture or unauthenticated smoke test.
